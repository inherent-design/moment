# Personal store and project identity

Moment keeps active intent and runtime state in one user-owned store. The user-facing entry point is `~/.moment/`; the default backing location is `~/.local/share/moment/`. These are two paths to the same data, not stores to synchronize.

## Discovery and relocation

Resolve the store in this order: an absolute `MOMENT_HOME` value, an existing `~/.moment` directory or resolvable symlink, then the default backing directory. Reject relative overrides, dangling links, and inaccessible destinations with an actionable error. Expand `~` in user-entered configuration before validating, without shell evaluation. Canonicalize the selected path once and display it in diagnostics.

First-time setup creates the selected store with user-only permissions and creates `~/.moment` as a symlink if that name does not exist. If an existing alias resolves elsewhere, preserve it and report the mismatch; an explicit override can still select another store for that process, but setup must not repoint the alias implicitly. Existing directories are never replaced by links. Native Windows implementations must use an explicit supported directory or junction strategy; this initial Unix-host layout does not claim Windows installation support.

Relocation copies or moves the complete store while writers are stopped, verifies manifest and database integrity, and updates the alias through an explicit operator action. Stable IDs remain unchanged. Restoring a backup on a second simultaneously running host requires a new system ID and an import procedure to avoid two independent writers claiming one identity.

## Layout

```text
~/.moment/                         user-facing directory or link
  registry.json                    store version, system ID, project locations
  contexts/<context-id>/manifest.json
  intents/<readable-name>.md        optional link to an incident's intent
  incidents/<incident-id>/
    manifest.json                  identity, context, projects, activation state
    intent.md                      readable purpose and completion contract
    checkpoint.json                current continuation state
    captures/                      selected attributable evidence, when needed
  runtime/                         database, socket, credentials, provider receipts
  artifacts/sha256/<digest>        future immutable admitted artifact bytes
  cache/                           regenerable bounded material
```

Registry, context manifests, incident manifests, intent, checkpoints, and a readable intent link form the documentation bootstrap. The implemented service uses SQLite under `runtime` for admitted state, event rows, receipts, execution outbox, durable schedule occurrences, messages, and delivery acknowledgments. Artifact storage and cache remain implementation work. Bootstrap files alone are not evidence of an active runtime incident or executed goal. Readable intent links are convenience aliases; they resolve to the incident's canonical file, preserve its identity, and must not overwrite an existing name.

## Bootstrap file contract

Every JSON file has `formatVersion: 1`. Unknown versions are refused rather than silently reinterpreted. All relative paths in manifests are confined to their incident directory after symlink resolution. Write replacements through a temporary file and atomic rename; serialize writers. Runtime adoption is explicit. Retain original intent bytes and source identity as attributed records, then create the incident through existing authenticated API authority. A bootstrap file cannot activate itself or grant permissions. The bootstrap reader can also retain exact manifest, intent and checkpoint bytes without activating an incident.

| File | Required fields and interpretation |
| --- | --- |
| `registry.json` | `systemId`, `projects`. Each project has `id`, `label`, `locations`, `origins`, and `contextIds`. Each location has `path` and `kind: git-worktree` or `directory`. |
| Context manifest | `id`, `label`, `projectIds`. Defines an association for saved intent; it does not instantiate a runtime `Context` or bootstrap authority. |
| Incident manifest | `id`, `contextId`, `projectIds`, `kind`, `contentPath`, `checkpointPath`, `status`, `activation`. `status` is `draft`, `ready`, or `archived`; `activation` is `manual`. These describe saved input, not runtime incident lifecycle. |
| Checkpoint | `stage`, `completed`, `next`, `blocker`. Optional `revision`, `evidence`, and `decisions` retain exact relevant identifiers. `completed` is an array of concise outcomes; `blocker` is a string or null. |

`intent.md` owns the active text. A tracked reusable template can seed it, but changes do not synchronize automatically in either direction. An optional manifest `sourceTemplate` object records the template's absolute `path` and `sha256` digest of its original bytes; relative links in the saved copy are resolved against that template's directory. The central store's format makes it possible to import the intent into a later Moment runtime without installing metadata in every repository. Saved content always enters that runtime as attributed input, not bootstrap policy.

New runnable goals and their continuation state belong solely in this central layout. A later goal gets a distinct incident and readable alias; completing a specification goal does not activate the implementation goal it writes. Repository-relative references in a central goal resolve through its registered project association. Keep specifications in the repository and personal task narration outside it.

Existing active goals in other project layouts remain in place until a canonical goal change or deliberate handoff. Introducing Moment does not move them, rewrite project instructions, pause agents, or synchronize their contents. At the handoff, identify the continuing goal's canonical location and retain selected source identity and unresolved state; avoid two independently editable task definitions. Retaining an old source for provenance does not keep it active. [Continuity between goals](integration.md#continuity-between-goals) owns the communication and handoff convention.

Project registration and context association remain explicit central operations. A general adoption command cannot infer a project's specification, ledger, goal or ownership conventions from its directory. Do not add repository markers or impose a uniform project layout to resolve that ambiguity. Prepare only the associations and admitted schemas needed by the next actual handoff, preserving other projects and existing authority.

## Project identity

A central UUID identifies each registered project. Paths are current locators. Git origins are discovery hints and may change, be absent, contain aliases, or identify several clones. A worktree belongs to a registered repository association while retaining its own locator. A branch name is not a stable project ID. Neither path ownership nor origin matching grants write authority.

On discovery, match a known canonical location first, then inspect Git repository/worktree identity and normalized origins for candidates. Multiple plausible matches remain unresolved until existing evidence or user guidance distinguishes them; never merge projects solely because their origin matches. Moves can update locators without changing identity after confirming the association. Copying a repository does not copy Moment authority.

Touched repositories need no `.moment` directory, `.git/goals`, marker, hook, or generated `AGENTS.md` section. Existing project instructions remain in force and can be referenced as evidence with revision and digest. Moment's own repository retains reusable documentation and contract examples.

## Legacy run payloads

The implemented [capture protocol](captures.md) separates compact historical meaning and evidence from bulky legacy payload representation. Its current-authority reader and owner-local exact-sharing helper preserve explicit disposition, custody and recovery. They are separate from the database migration and component retention below; public generic artifact/orphan-pruning APIs remain proposed.

## Runtime persistence and retention

The kernel uses SQLite WAL, `synchronous=FULL`, a five-second busy timeout and `user_version=2`. `snapshot_values` retains immutable canonical values under private integer keys and verified SHA-256 identities. Every `context_revisions` row retains a complete ordered manifest for its context value, records, assertions and control namespaces. Unchanged values are shared physically; logical identities, independent support, withdrawal, record/assertion order and historical revisions remain unchanged. There is no delta-replay chain. Bulk value reads share one consistent SQLite read transaction with the root; decoded occurrences are independent mutable objects, with no shared decoded cache.

`BEGIN IMMEDIATE` serializes admissions. New values, revision root, events, exact receipts and outbox entries commit in one transaction. Missing values, bad manifest/value digests, wrong system identity and unknown formats refuse rather than fabricate partial state. Private storage keys grant no access. Historical cursor reads retain current-policy checks. Format 1 requires explicit migration; ordinary startup does not convert or reset it. Transaction/termination tests are not evidence of power-loss behavior.

### Explicit migration and recovery

`moment storage plan [--enroll FILE] [--out FILE]` reads the selected store without starting a service. Its private plan identifies system/owner custody, source/target formats, effective memory limits, every retained revision and exact auxiliary/memory fingerprints. The target is kernel format 2 and memory format 3. Optional enrollment input is an array of explicit `{runtimeId, sessionId}` objects; no session is inferred from cache presence. The output remains reviewable JSON; `--out` exclusively publishes the same private plan.

Publish the matching build and stop only the authenticated, inspected Moment instance through the qualified lifecycle path. Do not restart Codex or peer goals. `moment storage migrate --file PLAN` requires quiescent writer/startup custody. A memory-only upgrade on an already-format-2 kernel preserves matching uncertain memory dispatch/labor custody without invoking a provider; other unsettled executions or labor still require settlement. The separate SQLite maintenance lock, consistent private backups, exact backup filenames, source/configuration checks and kernel/memory write transactions protect cutover. Competing changes, unknown ownership and unsupported layouts refuse. Original credentials remain in protected custody; database backups alone are not an independent recoverable installation.

The kernel conversion preserves every canonical historical state and exact receipt/event/import/outbox row. Memory conversion retains every original row byte-for-byte under its logical table identity, builds default working sets and immutable input bindings, and marks historical assessment basis honestly legacy. A renamed foundational session table fences stale format-2 session SQL. Kernel representation changes commit first; a separate checkpoint covers memory commit before the journal advances. `runtime/storage-migration.json` prevents service admission until both components, integrity checks, verified compaction and enrollment publication complete. `moment storage resume` uses the exact retained plan and verified converted fingerprints for forward recovery. Inconsistent backups require inspection and are never overwritten.

A completed older migration is preserved as `runtime/recovery/<old-plan-id>/completed-journal.json` before a new migration replaces the active pointer. Exact completed retries can read either retained receipt without replaying effects or overwriting later writes. An incomplete older format-2 plan still requires its qualified original recovery implementation; the new controller does not silently change its declared target.

Keep the original database and credential custody until the recovery disposition is qualified. After new writes, restoring the old backup directly would erase accepted state; use forward repair or a separately qualified import. Compression/cleanup must verify the exact original bytes and recovery path before removing an owned raw backup. Live journals, uncertain dispatches and referenced evidence cannot be discarded to reclaim space.

`runtime` also contains the private operator credential and registered delegate credentials. It is durable state, not a regenerable cache. Protect those files in backup and recovery; losing the operator identity does not automatically transfer ownership of existing contexts to a newly generated identity. Do not copy credential files into the source repository or ordinary captures. A deliberate credential rotation must preserve or explicitly recover the context's authenticated owner association.

The [managed lifecycle](managed-integration.md#service-lifecycle-and-custody) retains these identities across automatic startup. Its service logs are bounded and disposable; installation ownership receipts, interrupted config journals and uncertain retry inputs require their own protected retention. Integration removal preserves the central store. On-demand service startup does not guarantee timers run while the service or host is stopped.

The fixed verifier uses `runtime/verifier/<context-id>/<execution-id>/<attempt>/`. Private dispatch, status, and published receipt files are recovery evidence. Completed staging input and request files are removed only after admitted terminal reporting; the exact intent remains in the store. Failure diagnostics are private and bounded at 16 KiB. Receipt staging is validated before host publication, and an interrupted exclusive link is normalized on recovery. Cleanup must preserve unresolved dispatches and acknowledged receipts. Context and attempt directories never accept caller-selected path segments.

Live intent, current continuation state, unacknowledged messages, idempotency receipts, unresolved effects, active grants, and evidence supporting accepted claims are retained. Raw logs and caches have bounded retention profiles. Cleanup previews candidates with dependency reasons and removes only admitted, unreferenced, regenerable or explicitly expired material. Content deduplication does not erase independent evidence. Secrets are kept in host credential custody and referenced indirectly; they are not stored in goals or ordinary artifacts.

Generated review notes should be folded into their owning contract or checkpoint. Retain useful failure inputs and concise results instead of repeated full transcripts. Storage pressure may suspend new artifact-producing activity; it must not trigger deletion of recovery material or silently discard accepted work.

## Session memory storage

`runtime/session-memory.sqlite` is a component-owned format-3 SQLite store bound to the same Moment system identity. Private regular-file checks, WAL, `synchronous=FULL` and `BEGIN IMMEDIATE` protect local transactions; reads use a consistent SQLite snapshot. Exact original messages, associations, input/delivery state and receipts retain their existing identities. Shared immutable selection/profile/assessment values have verified digests and separately attributable working-set manifests. Focus and input bindings have independent state; a result cannot retarget its admitted input. Frequent cache changes create no semantic-context snapshot or full source copy. Formats 1/2 require explicit migration rather than automatic initialization.

Five entries per working set, eight retained sets per session, an 8 MiB component selection/manifest/focus-receipt budget, a 16 MiB assessment budget and a 1 MiB profile budget are initial defaults. The assessment budget counts payloads, manifests and input bindings with conservative metadata/index charges; it is not a measurement of SQLite file allocation. Keep the newest 32 eligible full assessments per session within the aggregate budget. Current set bases, in-flight/unknown work, profile dependencies and recovery material remain protected. Retired details keep bounded incoming-source handles and hashes. Full protection can refuse new preparation or settlement; it does not erase originals or dispatch another model call. Original source limits remain 64 KiB per source, 32 MiB retained source payloads, 128 sessions, 4,096 inputs/receipts and 64 pending inputs per session, 1 MiB checker input and 64 KiB checker output. Enrollment and focus retry receipts each have a 4,096-record cap. These component budgets are separate from native instance logs and actual disk allocation.

Working-set manifests can retain an existing work locator and source/capture guidance bindings with exact representation/digest, applicability and material omissions. Their metadata counts toward the component working-set budget; guidance bodies remain in their original component and are not copied into the memory store. Current authority/freshness qualifications are computed for the selected set on each read, rather than persisted as permission grants. A metadata-budget omission can hide the complete served binding under `/bindings` while retaining its recovery qualification. Existing cache migration creates default sets without inventing bindings or inferring past source use.

Operator limits live in the optional private `runtime/session-memory-limits.json`, independently of provider credentials: `{"formatVersion":1,"limits":{"maxWorkingSets":8,"maxAutomaticBytes":4096}}`. Omitted keys use implementation defaults; unknown keys, unsupported versions and invalid bounds refuse. `maxAutomaticBytes` controls the complete automatic UTF-8 presentation, including its preface, from 1 KiB through 256 KiB. It neither describes model context capacity nor changes explicit read ceilings. The full numeric limit names are owned by `memoryDefaults` and `MemoryLimits`; ordinary reads report the effective presentation preference. A changed effective configuration invalidates an uncommitted migration plan.

Enrollment is stored independently of cache revision in `metadata`, with its actor, generation and latest admitted automatic intake. New sessions default off. A private atomically replaced `runtime/session-memory-enrollment.json` projection lists enabled sessions for the hook's cheap disabled path; it is a hint, and intake rechecks the authoritative enabled state and configuration revision in its transaction. Publication failure reports an uncertain configuration outcome and preserves the exact retry. Disabling cancels queued automatic inputs with explicit gap disposition while retaining explicit manual inputs, original history and already-dispatched unknowns. `runtime/session-memory-configuration/*.json` retains uncertain CLI configuration requests; use `memory configure --file` with the original revision/key, rather than generating a second toggle.

Eviction changes automatic cache inclusion; the selected source remains recoverable while retained. Reconstruction reuses original source IDs or admits explicitly selected history text with original session attribution and immutable exchange references. A source part's optional JSONL selection metadata identifies the retained view, raw frame digest and per-part provenance/content kind; it is not a claim that an entire message or conversation was imported. Read packets report selected-input coverage, pending inputs, failed/cancelled gaps and gap omissions. A callback's native turn ID is correlation metadata, and identical text does not deduplicate distinct submissions.

A dispatch retains its exact cache/input basis and prompt/schema/provider identities before inference. Unknown completion reserves the single checker slot across restart until evidence reconciles it. An unchanged result advances the processed-input receipt without advancing cache-content revision. Successful receipts also retain the bounded checker-reported explanation; the session row keeps the latest successful assessment and its input sequence for constant-time reads. Updating that assessment is metadata, including when the list is unchanged. Failed checks preserve the earlier assessment. Legacy rows/receipts have no fabricated explanation. These strings add to receipt/state overhead, outside the source-payload bound. Pending work, original receipts and uncertain provider evidence have recovery significance. `runtime/session-memory-intake/*.json` contains exact private requests after uncertain hook intake; replay only the retained input and delivery identity. Cleanup must preserve these inputs and the active dispatch.

`runtime/session-memory-native/jobs/*.json` retains private native dispatch/result journals, including logical session/sequence, observed terminal status, valid output and its digest. Model JSON rejects duplicate keys and unsupported Unicode before admission. A durable completed observation or interruption can reconcile a lost acknowledgment without inference; a closed process alone does not establish a model outcome. Publication syncs the replacement file and its directory before dependent operations; no power-loss test is claimed. The memory provider caps individual journals at 512 KiB, reserving JSON-encoding overhead for a bounded raw result; the guidance provider retains its separate 128 KiB cap. Before starting inference, its default 4,096-file and 16 MiB journal budgets reserve a full record; exhaustion leaves pending work and the prior cache intact. These bounds are separate from source-payload limits and include neither native instance logs nor SQLite overhead. Settled native instances are removed. Unknown instances remain recovery material; 64 retained instance directories refuse new startup rather than permitting unbounded orphan preparation. An older settled instance is removable only after its retained process is observed absent and its private component/dispatch marker matches; a retained PID never authorizes killing a process. The provider never prunes uncertain state to free capacity.

## Candidate-service storage

Source definitions and immutable capture metadata use the existing governed kernel store. Whole/selected representations and projected/raw results live in `runtime/guidance/bytes/<digest>` with private exclusive publication and integrity checks. Default component bounds are 32 MiB, 8192 bodies and 256 KiB per body. Repeated unchanged observations deduplicate their capture and bytes; the latest observation remains separate. Metadata is bounded to 256 registrations and 2048 captures per context. Large bodies are not copied into every semantic snapshot.

`runtime/guidance-native/dispatches/<dispatch-id>.json` retains exact composed input and execution/attempt correlation before invocation, bounded to 4096 files, 16 MiB total and 240000 bytes per composed dispatch. `runtime/guidance-native/jobs/` uses the common native engine's bounded result journal and isolated instance custody. Guidance profile 1 retains its raw and parsed result. Memory native profile 5 transfers matching raw/decoded outcome evidence to the assessment store before eligible native-journal payload cleanup. `runtime/native-labor.json` holds the shared component/dispatch/input identity while native outcome is uncertain. A memory result committed before native cleanup has an attributable retained settlement, so restart can release the same slot without another inference.

A digest locates private bytes only after current source/task/work access. Capture integrity, latest observation, result staleness and current permission are distinct. Unavailable bodies become explicit read omissions; metadata and earlier authorized captures remain useful. `guidance.read` supports selected/whole representations and UTF-8 ranges without exposing a generic file or artifact API. Cursor pages recheck current visibility and report each page's revision.

Storage exhaustion refuses new intake/dispatch without deleting accepted or uncertain evidence. There is no age-based pruning. Before any manual orphan cleanup, preserve the complete store and qualify references from retained captures/execution outcomes, native dispatch/result journals and outstanding publication/recovery. Settled owned native instances use observed process death plus matching private markers; a PID is never a process handle. The separate public artifact and normative retention APIs remain proposed.

## Proposed guidance and work storage

The [guidance package](guidance.md#dependency-and-retention-behavior) adds ordinary immutable source/target/binding/adoption/assessment records and rebuildable discovery indexes. The referenced SQLite revision strategy and central artifact custody remain the baseline. Index frontiers, source gaps, and current support determine truthful completeness; an index is not a separate authority. Cross-context projections require the explicit proposed boundary rather than direct foreign-reference lookup.

[Work providers](work.md#resource-and-recovery-policy) retain exact input bases, dispatch/attempt descriptors, native references, result/usage receipts, and partial publication journals. Provider recovery data is protected while dispatch or effects are uncertain. Selected raw sources can expire only after dependent accepted meaning/evidence and recovery needs are reconciled under the retention policy. Goal drafts and task checkpoints remain personal central state; reusable templates and contracts remain tracked reference material. This package adds no repository marker, automatic cleanup, native-goal activation, or whole-host transcript import.
