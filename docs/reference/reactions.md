# Reactions and execution

Reactions respond to changes relevant to an incident. They can propose a semantic change, arrange an execution, refine a view, or leave an incident resting. Runtime scheduling implements those decisions within current authority and measured resource limits.

## Proposal and commit

`reaction.evaluate` is a bounded, read-only evaluation of an immutable rule against a snapshot and named events. It returns eligibility, an explanation, and optionally a candidate operation input. A false condition is ineligible; unresolved observations with no later positive match return `POLICY_INDETERMINATE`. It does not call a model or execute the operation. The destination must be an implemented Moment method. Literal input is copied, then registered bindings replace existing JSON Pointer locations; missing locations, overlapping pointers, and unsupported bindings are invalid. Result validation uses the destination's schema.

The current rule implementation accepts implemented Moment methods as destinations. Use `execution.request` to express a capability invocation with an exact advertisement and grant; direct capability-name destinations remain unsupported. It processes eligible named events in sequence order and returns the first matching candidate. With no event types and no event IDs it evaluates once against context bindings. Bindings include `contextId`, `principalId`, `incidentId`, `action`, `resourceRefs`, `contextRevision`, `now`, and event `id`, `ids`, `type`, and `subjectRefs`. Event-specific bindings are unavailable for eventless evaluation. Input bindings are limited to 64 nonoverlapping paths with at most 64 pointer components. Candidate schema validation does not authorize its eventual execution; calling the destination rechecks authority.

`transition.propose` records a candidate with explicit changes, execution intents, evidence, and exact policy and rule references. Its `basisRevision` must equal the request's `expectedRevision`. The proposal is validated but has no domain effects. The proposal write advances the context revision once. `transition.commit` may commit only while the current revision equals the proposal's recorded revision and its admission checks still pass. A changed context requires a new proposal using fresh evidence; the old proposal is not silently rebased. This coarse guard is an initial correctness choice, not a throughput claim.

Commit atomically writes admitted semantic changes, control changes, execution intents in an outbox, and emitted events. A failure writes none of the proposed domain change. A rejected proposal can retain its explanatory rejection in a separate admitted control transition. Empty changes and executions are invalid for a proposal. A committed proposal returns its original receipt on an exact retry.

Semantic proposals and execution intents are implemented. Proposing validates the combined execution reservations without reserving or dispatching; committing stores the graph, execution states, and outbox atomically. Intents share the proposal's incident and retain the proposer's grant authority. A different reviewer needs current execution-request permission and, unless the operator, explicit visibility of that grant. A stale or refused attempt leaves the original proposal unchanged rather than storing a rejection through an unauthorized write. An attached rule identifies provenance; it does not certify that the proposer derived its changes from that rule. A proposer can read its retained proposal through the originating grant branch, including after another authorized reviewer commits it. Other branches need explicit proposal visibility. All reads and commits still require current action and incident admission. The stored commit receipt and returned receipt are identical and persist atomically with the graph change.

`graph.transact` provides the same guarded atomic admission for direct graph changes without creating a separate proposal. `execution.request` provides it for one execution intent. None of these operations promises an atomic transaction with the external world.

## Capability negotiation

`capability.advertise` records an immutable advertisement from its authenticated provider with exact admitted input/output schemas, features, isolation and expiry. Names cannot collide with installed protocol methods. Publication checks current policy, schema visibility and evidence; it is bounded to 4,096 retained advertisements per context. An advertisement describes an offered contract rather than proving host isolation or available resources.

`capability.match` considers readable advertisements with the requested name under a current validated grant chain. It retains ordered unmet reasons for version, exact input/output schema identity, features, isolation, expiry and grant action/resource scope. An incident-restricted chain without an incident adds `incident_required`; a compatible candidate then remains `unknown`. Current policy is evaluated only for an otherwise compatible and scoped candidate. Indeterminate policy returns `policy_unknown` with unknown eligibility, while a known refusal returns `policy` with ineligible status. Discovery never reserves resources or admits an execution.

Results rank eligible, unknown and ineligible candidates in that order, then fewer unmet reasons, then stable advertisement identity, before applying the result limit. An advertisement expires inclusively at its declared instant. Later execution admission rechecks current authority, context/incident state, advertisement, input schema and all resource envelopes. A prior match is evidence for selection, not a permission receipt.

## Execution lifecycle

| Current state | Admitted next state | Trigger |
| --- | --- | --- |
| `queued` | `leased`, `cancelled` | Claim or cancellation before dispatch. |
| `leased` | `running`, `cancel_requested`, `cancelled`, `unknown` | First heartbeat marking dispatch, cancellation, confirmed pre-dispatch cancellation, or lost lease. |
| `running` | `succeeded`, `failed`, `cancel_requested`, `unknown` | Outcome receipt, cancellation, or lost lease. |
| `cancel_requested` | `cancelled`, `succeeded`, `failed`, `unknown` | Observed outcome; cancellation can race with completion. |
| `unknown` | `succeeded`, `failed`, `cancelled`, `queued` | Evidence-backed reconciliation; requeue only when non-execution or safe idempotent replay is established. |
| `succeeded`, `failed`, `cancelled` | *none* | Terminal for this execution ID. A new admitted intent may request another execution. |

Claim binds the authenticated advertised provider to one execution and increments its fencing token and attempt number. The provider's credential authority is separate from the requester's execution grant. A heartbeat extends the lease subject to limits and marks a leased execution running before any external effect. The worker verifies that heartbeat succeeded before dispatch. A success or failure before that heartbeat is invalid. Every finish or heartbeat must present the current lease ID and fencing token. Expired or replaced leases return `LEASE_STALE`. Reconciliation additionally names the exact attempt; a report for an older attempt cannot settle a newer unknown attempt. Older observations can remain separately attributed evidence through ordinary graph operations.

Lease requests are 1–30,000 milliseconds, bounded further by the advertisement, grant-chain expiry, and execution deadline. Within a runtime boot, monotonic expiry remains effective if the wall clock moves backward. A different boot makes retained leases unknown immediately. The daemon maintains one timer for the next known execution deadline and performs recovery at startup; it does not poll a model. It emits a durable `execution.recovered` event when maintenance changes state. A failed maintenance attempt reports an operational error and retries its retained deadline. Unknown executions are never automatically claimed again.

The lease window uses one validated wall/monotonic/boot observation. Its integer millisecond interval is derived before interpolation into the fractional monotonic frame; epoch-scale arithmetic must not alter that origin. Expiry is inclusive in either clock frame. Fencing counters remain exact safe integers and cannot wrap or advance beyond their representable limit. An unknown execution retains a wake-up for its intent deadline until cancellation is recorded; that observation preserves uncertainty and then rests without an immediate timer loop. Terminal work schedules no further lease/deadline recovery.

Lease expiry does not establish that an effect failed or never happened. It produces `unknown` and asks the adapter to reconcile. Providers declare lookup, idempotent replay, or manual reconciliation support. A provider with neither lookup nor idempotency leaves uncertain effects unresolved until discriminating evidence arrives. `execution.reconcile` is restricted to the provider or delegated reconciliation principal. An `observed` resolution records its outcome, including continued uncertainty. A `retry` resolution requires evidence for its `not_started` or `idempotent` basis and fresh admission before requeue. Retry preserves the external idempotency identity for this execution.

Cancellation is a recorded request to stop. The adapter reports what happened. It may be impossible to reverse a completed action. Ending an incident, closing a context, or revoking an execution grant cancels undispatched work and requests cancellation for leased or running work. An unknown effect remains unknown. Confirmed completion after a cancellation request remains completion. Undispatched expired grants or advertisements cancel their queued work. Context closure blocks new effects while preserving currently authorized finish, observed reconciliation, and cancellation operations; it never permits retry into the closed context.

`Execution.cancellation` retains the first admitted cancellation request separately from observed state. Cancelling an unknown execution therefore leaves it unknown while preventing a later retry from reviving that intent. A subsequent observed success can still resolve uncertainty truthfully. Execution-only proposals require execution authority; they do not additionally require graph-mutation authority when no graph changes are present.

## Scheduling

`schedule.put` binds an immutable rule to an incident and wake condition. The ID identifies that exact schedule content; replacement uses a new ID after cancellation. Installing a schedule does not immediately satisfy an event trigger from historical events. The installation revision becomes its baseline. An `at` trigger already due becomes eligible once; an `after` trigger can refer to a retained earlier event.

The implemented scheduler binds the creator and its exact grant branch at installation. It rechecks schedule admission, rule access, deterministic evaluation, and destination authority at dispatch. Event and relative-anchor schedules additionally require `events.read`. Ending the incident or closing the context cancels future schedule admission. `schedule.get` exposes authorized status, pending occurrence identities, currently visible active execution identities, and the last bounded fault. Cancelling a schedule leaves admitted executions to their separate cancellation API.

An event trigger filters event type and subject selection. `each` admits one trigger occurrence per matching event. `edge` evaluates whether the selector has any current visible matches and fires on a false-to-true transition after installation. Repeated true states do not fire. Selector evaluation uses the schedule owner's current authorization. Withdrawal can reset the edge. Persist the baseline and last evaluated event sequence.

Selectors use the retained snapshot at each source event, with current visibility. This preserves an intervening false edge even if later writes arrived before the scheduler ran. Initial edge state reflects the installation snapshot. Capacity wakes track false-to-true availability in the remaining logical context/policy/grant reservation envelopes, initially firing if sufficient capacity already exists. Resource names are the six numeric `Limits` fields; this is not a measurement of physical host availability. Absolute and relative timers currently require `once`; a repeated timer needs a new schedule and anchor.

Relative anchors admit a zero-millisecond gap and refuse an out-of-calendar sum before storing schedule state. Capacity remainders and compound outgoing reservations use exact safe-integer accounting, including explicit overflow. A scheduled operation's outbox must collectively fit its rule envelope; individually fitting intents are insufficient. Refusal preserves the pending occurrence and records a bounded fault without partially admitting the proposal or its effects.

`once` completes after its first admitted reaction, including a reaction that produces a definitive ineligible result; a transient error retains its pending occurrence. `rearmAfterCompletion` admits no overlapping reaction from that schedule. With `coalesce`, multiple pending triggers combine into one occurrence carrying their event IDs; otherwise retain bounded pending occurrences. Repeated timer schedules require a new temporal anchor after completion; rearming an already-fired absolute deadline is invalid. Queue capacity is a profile limit; overflow returns a visible `LIMIT_EXCEEDED` event and preserves a rescan cursor rather than dropping work silently.

Each occurrence is a durable `runtime.schedule.triggered` event. Its consumption, operation effects, outbox, and receipt commit in the same transaction. A restart therefore retains either the pending occurrence or its admitted result. Scheduled rules target installed context mutations. The dispatcher enforces the same context, refreshes `expectedRevision`, and derives `idempotencyKey` from the occurrence identity. Additional trusted bindings are `occurrence.id`, `occurrence.eventIds`, and `schedule.id`; use the occurrence ID for a fresh execution or record identity. Direct rule evaluation does not invent those bindings.

The operation's actual execution reservations must fit the rule envelope in aggregate. Rearming waits until executions admitted by the prior operation are terminal; unknown work remains active. A definitive false rule consumes the occurrence without invoking its destination. Indeterminate evaluation, unavailable authority, or refused effects retain it with a bounded fault and await new relevant activity, without a retry timer. Runtime bookkeeping events do not retrigger their own scans.

Initial bounds are 128 retained schedules per context, 128 pending occurrences per schedule, 32 source IDs per coalesced occurrence, 256 source events per scan, and eight operation admissions per daemon pass. Overflow retains the source cursor and emits a fault accessible through events and schedule status. The daemon yields between passes. It suppresses automatic feedback when a source's causal ancestry already includes that schedule, including cycles through other schedules. An unresolved or over-128-event ancestry waits with `POLICY_INDETERMINATE`. Fresh external observations can continue work; these guards do not create an idle inference loop.

A full queue waiting on prior execution records its observed activity revision and rests without acknowledging the omitted source. New activity permits reobservation; completion releases space and the retained cursor recovers the source. Failed capacity enqueues retain the unacknowledged rising edge. Recording a dispatch fault also requires the same current mutation basis and pending occurrence: cancellation or an intervening revision makes a delayed fault stale. Causal matching uses full schedule reference identity, and repeated ancestry pops count toward the declared bound.

The initial scheduler chooses the oldest queued occurrence within an incident and uses a persisted round-robin cursor across incident IDs. Execution admission retains the context's concurrency bound. Priority or cost heuristics can be added through policy after measurement. Selection never changes admission. Reevaluate policy, current grants, capability freshness, and capacity when dispatching.

## Budgets and rest

All `Limits` values are nonnegative safe integers. Zero means no allowance, not unlimited. Limits on a context are shared aggregate envelopes; an execution requests a reservation within them. CPU, model-token, output, and spend limits are cumulative within each context and grant, including descendant grants; memory and concurrency bound simultaneous reservations. Execution limits bound that execution across attempts. Operator-only `context.limits` can revise an envelope with evidence; it preserves cumulative usage, reservations and currency and refuses a deadline that invalidates retained execution. A new grant or envelope revision does not reset consumed context resources.

`Execution.usage` records cumulative provider-reported CPU, output, token, and spend counters, plus peak memory. `execution.finish` and `execution.reconcile` require these counters; reports cannot decrease known usage. Requests and retries must fit reservations. Observed reports may disclose an actual overrun: `Execution.limitViolations` retains the exceeded fields without changing the observed semantic outcome, and further dispatch in that context stops. An overrun does not expand authority or silently reset a budget. Successful JSON output and failure/unknown detail must fit reported output bytes. Queued work is known not to have executed and starts at zero. Unknown reports can carry known lower bounds while retaining conservative reservations.

Every nonterminal execution holds at least its full cumulative envelope and its memory/concurrency reservation, or larger known usage. Terminal work retains charged cumulative usage and releases unused allowance and active memory/concurrency. This initial policy reserves one slot even while queued; it favors a conservative bound over a deep runnable queue. Retention currently admits at most 4,096 executions per context and does not silently delete receipts to recover capacity.

Accounting validates authenticated provider reports. It does not independently enforce OS CPU/memory limits. A concrete provider must report its actual measurements and enforcement limitations; claiming a hard host limit requires that provider's execution evidence. The installed byte verifier has actual process, measurement, permission-guard, and receipt-recovery tests, with its limits described in [integration](integration.md#local-byte-verifier).

Reserve before dispatch, settle measured usage, and release unused reservation when the outcome permits it. Unknown outcomes retain a conservative reservation until reconciliation. Spend microunits use the declared currency; currency mismatch refuses admission. A provider without reliable pre-call cost or usage bounds cannot promise a strict spend ceiling and must not be admitted under a profile requiring one. Subscription capacity and billed API spend are recorded separately.

When no eligible activity can advance an incident, retain its continuation references and wake conditions, set it resting, and release active compute. Rest needs no model polling. Resource availability, user input, new evidence, or a declared deadline can wake it. The user may complete or cancel an incident at any time under their authority. A host that is offline retains pending intent and reconciles missed deadlines on restart rather than inventing completed work.

## Purpose reconciliation

The proposed [purpose model](purpose.md) uses maintained criteria and finite work without adding mandatory runtime phases. [Work reconciliation](work.md#evidence-triggered-reconciliation) binds selected source changes to assessments, investigations, and guarded repairs through these existing scheduling/lease semantics. The new work destinations, qualified source observations, provider, and profile checks still need implementation. An existing schedule or prompt renderer does not itself supply model dispatch, a filesystem watcher, physical-capacity telemetry, or automatic native goal activation.
