# Hosts agents and system exchange

Adapters connect Moment's governed operations to concrete execution platforms. An advertisement describes a possible capability; current evidence, permission, capacity, and provider authentication determine whether it can execute.

The managed MCP bridge and checked operation bindings provide explicit attachment, bounded context, on-demand lifecycle and selective agent discovery. [Managed integration](managed-integration.md) owns these surfaces and human commands. Explicit-root installation preview/apply/remove and actual isolated Codex MCP continuation/child use are exercised in owned temporary roots. Installation and adoption of existing goals are separate operations. Existing native invocation and verifier behavior below remain implemented.

## Capability negotiation

`capability.advertise` binds the advertisement to the authenticated provider. Names, explicit supported versions, schema digests, required features, and acceptable isolation kinds must match a `CapabilityRequirement`. Version strings are exact values in `0.1`, not implicit semantic-version ranges. An advertisement expires and must be refreshed by publishing a new immutable advertisement ID. Old execution intents retain their exact reference but require a still-valid compatible admission before dispatch.

`capability.match` returns eligibility and unmet requirements. Capability fit and permission are separate checks. The caller selects a candidate; the scheduler rechecks it when claiming and dispatching. An imported advertisement is evidence about a remote capability, not an installed local provider or permission to contact it. Peer configuration binds actual providers to authenticated endpoints.

The implemented registry retains at most 4,096 advertisements per context, forbids names colliding with protocol methods, and validates exact input/output schema references. Publication cannot impersonate another provider. Grant actions may name an advertised capability; publication does not add that action to the active policy. A caller still needs both the explicit action permit and a grant covering the advertisement and incident before queueing work.

Matching considers authorized advertisements of the requested name, reports exact version/schema/feature/isolation mismatches, and orders eligible candidates before unknown and ineligible ones before applying the result limit. Its optional `incidentId` supplies incident-specific admission context. Without it, an incident-restricted grant produces unknown eligibility. Delegates can match only their bound grant. Matching reserves no resources and authenticates no external implementation; claims recheck the exact advertisement, execution grant, policy, input schema, and incident state.

## Host adapter

`HostPort.inspect` reports observed platform and resource measurements with units, timestamp, and source. Missing measurements stay unknown. Memory, disk, CPU, available subscription quota, and billed usage must not be invented from guessed token counts or previous snapshots.

`HostPort.execute` receives the execution, admitted grant, and policy reference. The adapter resolves resource references to installed resource descriptors. A filesystem descriptor binds canonical roots, permitted read/write operations, and symlink handling; a process descriptor binds an executable or command template, argument schema, working-directory roots, allowed environment names, network policy, and output limits. Descriptor changes require admission and an updated reference. An agent-supplied shell string cannot substitute for an admitted descriptor.

Resolve paths and mounts at dispatch, then enforce them with the strongest available host mechanism. A directory label or Git worktree is not a sandbox. `isolation: none` explicitly represents host execution; policy decides where that is acceptable. Container and VM providers must establish actual boundaries through execution tests. Graphical execution is a capability using a display/browser endpoint inside its admitted environment; it is not part of the core scheduler.

Dispatch uses a durable execution ID as the external idempotency identity when the provider supports one. Fencing tokens stop stale workers only where the provider or adapter can enforce them; they cannot revoke an arbitrary external process by themselves. Cancellation and reconciliation follow [reactions](reactions.md). Model output, stdout, screenshots, and traces enter as attributed observations with bounded artifacts.

Host and agent adapters return an `ExecutionReport` containing exact attempt, outcome, and cumulative usage. Reconciliation returns a `ReconciliationReport` with attempt, resolution, and usage. The adapter retains discriminating receipts and submits them through the ordinary finish or reconciliation API. The first concrete implementation is the fixed local verifier below; generic shell, VM, graphical, and model providers remain separate work.

## Local byte verifier

`local.verify-bytes` version `1` accepts canonical base64 and an expected SHA-256 digest, up to 262,144 decoded bytes. Its exact installed input, output, receipt schema, worker source, Node version, platform, and process descriptor determine compatibility. The advertisement must belong to the local authenticated operator and match that descriptor. A lookalike name or a changed schema does not select this adapter. No caller-selected code, file path, executable, arguments, or environment is forwarded to the worker.

`installVerifier(root, contextId)` in `runtime/providers/bytes-runtime.mjs`, also exposed as `pnpm moment verifier <context-id>`, is an explicit owner bootstrap through the ordinary API. It publishes the three immutable schemas, advertises the capability for 24 hours, preserves current denies while adding an owner permit for that action, and issues a nondelegable grant restricted to that advertisement and `execution.request`. The grant retains the current aggregate policy envelope; the returned execution limits are smaller per-job reservations. Reinstallation does not reset consumed context resources. Credentials remain in the private owner file rather than command parameters or worker inputs.

The daemon runs one fixed verifier process at a time, selecting contexts in round-robin order and queued work in outbox order. It stages bytes under its own private job directory and supplies only `LANG` and `TZ` in the child environment. Node permission flags restrict filesystem APIs to staged reads and receipt staging writes and deny network, subprocess, worker, native-addon, inspector, WASI, FFI, and OpenSSL STORE access. A 32 MiB old-generation heap setting and a five-second observed wall timeout supplement the bounded input. Node's permission model guards trusted code; it is not an OS sandbox for hostile programs, and the heap setting is not an RSS ceiling. [Node permission model](https://nodejs.org/api/permissions.html)

The worker samples `process.resourceUsage` after verification and before receipt persistence. CPU is reported in rounded-up milliseconds and peak RSS in bytes, converted from Node's KiB measurement. Its receipt states that scope and the actual Node version. Host scheduling, staging, and finalization overhead are outside that sample. The fixed operation invokes no model or billed API. CPU and RSS are metered facts, not hard OS enforcement claims. Missing measurements remain unknown; an incomplete process does not manufacture a zero-cost terminal result. [Node process resource usage](https://nodejs.org/api/process.html#processresourceusage)

Before spawning, the host fsyncs a dispatch marker. The worker writes a complete `receipt.ready` staging file. Because permission mode disallows `fsync` on the tested Node version, the host validates its schema, attempt, intent digest, descriptor, result, and actual input bytes, then fsyncs and exclusively publishes `receipt.json` and syncs the directory. Recovery normalizes an interrupted publication without overwriting different bytes. Only that validated receipt settles completion. A retained dispatch without a receipt remains unknown and is watched for later publication; it is never blindly rerun. Proven absence of a dispatch can support a freshly admitted `not_started` retry. Receipt watches are bounded at 64 and invoke no model polling.

Provider receipts and lookup observations become independently attributed semantic records when graph admission allows them. If finalization outlives graph-write authority, such as after context closure, its evidence instead binds the existing capability descriptor and retained receipt digest. Authorized finish/reconciliation can still record the observed outcome. Cancellation never turns an already completed hash check into rollback. Corrupt receipts, stale attempts, conflicting identities, symlinks inside job paths, hardlinks outside the publication protocol, and permission-glob syntax in locators refuse automatic settlement. The central home alias is resolved before creating job paths.

## Agent adapter and prompts

`AgentPort.invoke` receives a prompt artifact, execution, and grant. The prompt contains the intent, selected evidence, admitted actions, output schema, current constraints, and continuation references. It can request a proposal or observation, not directly write privileged store state. Tool use within an invocation must pass through the same adapter admission or be bounded by the host's independently configured permissions.

`prompt.compose` is deterministic rendering. Its template is an admitted `moment.prompt-template` atom whose value contains a UTF-8 `text` string and an ordered `sourceSlots` array. Each slot is a unique identifier matched to the corresponding entry in `sourceRefs`. The installed schema is available to new contexts; existing contexts can explicitly publish its unchanged definition. Templates require current support from an admitted `authorityIssuers` principal, including for historical rendering. A delegate’s own assertion does not promote its instructions. Templates use only `{{slot}}` replacement with the canonical JSON representation of the authorized source; no expressions, includes, filesystem reads, or executable evaluation. Unknown or missing slots are invalid. The content is a canonical JSON envelope with `instructions.templateText`, `quotedEvidence.rendered`, the incident, current policy reference, intersected grant limits, grant action ceiling, and the output schema document. Trusted template instructions and quoted evidence occupy separate named sections. Retrieved evidence cannot redefine the surrounding instructions.

The template defines optional slots explicitly with an `optionalSlots` array. If the final UTF-8 content exceeds `maximumInputBytes`, omit optional slots from last to first, replacing their marker with `[omitted]`, and report their references in `omittedRefs`. Required content that still exceeds the budget returns `LIMIT_EXCEEDED`. The digest covers the exact rendered content, template reference, sources, omissions, and output schema. This is a byte bound, not a tokenizer estimate. The service supports up to 32 sources and 256 KiB of content. Every source is authorized before optional omission; omission is not a way to hide inaccessible dependencies. Input and output schema references remain exact and immutable. Rendering invokes no model, filesystem read, include, or expression evaluator.

Callers select the template and applicable sources. For goal consolidation, an applicability review can distinguish carried principles from local, superseded, or irrelevant details, with the current purpose's material constraints in required slots. Reobserve source locators when freshness matters and admit changed bytes under new immutable record identities. Composition retains the selected captures even if their original files change. A later producer generates the answer and verifies its shape and meaning.

A curated guidance consumer can use these installed primitives directly. Retain its source-based applicability review as ordinary evidence, support a `moment.prompt-template` under current issuer authority, and connect that template to its selected purpose/sources with `moment.derivedFrom`. A `graph.query` selector with `schemaNames: ["moment.prompt-template"]`, `relatedTo: purposeRef`, `relationRole: "source"` and `assertionStatus: "asserted"` retrieves matching neighboring template records. The caller then binds the selected sources in `sourceSlots` order and invokes `prompt.compose`. Connectivity provides retrieval leads; it does not establish applicability or issuer authority, and the assertion filter applies to returned records. Composition independently checks current template authority. This arrangement uses no new schema, resolver, worker or compulsory workflow.

Support citations in `assertion.evidence.sources`, references inside atom payloads and incident continuations do not implicitly create graph adjacency. `relatedTo` follows explicit relation endpoints. When an artifact should be rediscovered from its purpose, retain its actual derivation through `moment.derivedFrom` with `result` and `source` roles. This makes the artifact a retrieval candidate; it does not establish current applicability or instruction authority. Related endpoints are context-local. A native agent can combine separately authorized reads with canonical project instructions in its own working context without merging contexts or transferring permissions.

The current main-agent consumer exercised this path in one research context, compared admitted captures with their live local bytes, and produced an attributable guidance brief from the composed artifact. It retained documentation/continuity aims while excluding web-only instructions and identifying superseded local storage and read-policy directions. The brief and exact tool evidence are retained centrally. Source selection and semantic review were manual; this is not a blind comparison, automatic extraction, automatic freshness, cross-project discovery or measured improvement in agent behavior.

Prompt selection can begin as policy over context, evidence gaps, recent outcomes, and capacity. Model-assisted template generation is an ordinary bounded execution; its output is a candidate template requiring schema and policy admission. There is no mandatory sequence of brainstorm, research, review, and finalize modes. Select behavior because it addresses the current condition, and retain evidence needed to evaluate whether that choice helped.

## Codex boundary

The native client and managed MCP adapter run alongside native Codex usage. Opt-in isolated app-server checks exercise the original dynamic-tool connection and the actual SDK MCP path, including persistent continuation and one native child. Automatically managed model threads, goals and model-provider dispatch remain future work. Generate the installed Codex schema and qualify the exact methods used before changing the integration. Private internal agent tools are not assumed to be an external API. [Codex app server](https://learn.chatgpt.com/docs/app-server)

Keep Codex authentication within supported Codex flows. Subscription usage and separately billed API labor remain different budgets; using a daemon does not provide unlimited inference. Full-approval Codex operation is owner-reported host configuration, not evidence that a sandbox exists. Moment's narrower execution policies govern admitted Moment operations; direct host tools retain their actual host authority.

Real Codex verification uses a dedicated app-server process, never the owner's primary managed daemon. A direct `codex app-server --listen stdio://` process supplies a private pipe transport. Its child environment selects a separate Codex state root, and its working directory is a disposable test workspace. Do not use the managed daemon's proxy, default control socket, shared writable configuration, or primary sessions. The installed binary can be read and executed without modification; record its actual version and qualify the installed protocol. Protocol initialization can be tested without logging in. Live inference additionally needs a supported independent authentication path that does not rotate or rewrite the primary session. [Codex environment variables](https://learn.chatgpt.com/docs/config-file/environment-variables)

`isolatedCodex` in `runtime/codex.mjs` is a native connection with a declared interface, not an automatically dispatched `AgentPort` model provider. The caller supplies only an access token/account pair and explicit function tools backed by its own restricted Moment client. Up to eight distinct function tools validate arguments and bound responses to 256 KiB; a turn accepts at most 16 KiB of instruction and a deadline of 1–120 seconds. Unknown server requests, including refresh requests, are refused. The connection uses ephemeral auth storage and deletes only its own workspace/state on `close`; callers must close in `finally`. Timeouts require reconciliation of any submitted Moment mutation, not blind turn replay. Model work through this connection uses the subscription outside Moment execution reservations; it makes no claim of measured model cost or hard model-token enforcement.

The opt-in `pnpm test:codex-native --credential-file /absolute/private/auth.json` explicitly reads a private owner-controlled source, selects its unexpired access token/account only, and never forwards refresh/session storage. It first observes no inherited account. Native Codex retrieves an actual verifier receipt using `moment_context`, submits a schema-validated attributed observation with `moment_observe`, and the check retrieves that observation after a Moment restart. Credentials and raw protocol diagnostics are never printed or captured. Ordinary tests remain independent of Codex and credentials. This path records its actual executable version and local consumed-API contract digest, then validates the requests/results it uses. It accepts compatible release changes and refuses actual API disagreement. Experimental host-managed token authentication remains distinct from ordinary CLI sign-in; executed evidence is scoped to its observed environment. There is no automatic fallback to copying auth caches or sharing refresh state. [Official external-token flow](https://learn.chatgpt.com/docs/app-server)

Saved goal text is reusable input. Creating a file does not activate a Codex goal or schedule an agent. A user can explicitly point `/goal` at the central intent file when ready. [Using goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

## Continuity between goals

Introduce Moment when a canonical goal changes or the current participant deliberately hands work off. An existing active goal keeps its current definition and location until that boundary. Record a reference and exact source basis when useful; do not create a second independently editable goal. New central goals follow [storage](storage.md#bootstrap-file-contract). A handoff records what is carried forward, what is complete or superseded, and what remains uncertain without silently changing scope or completion criteria. Mere file creation, message delivery or tool availability activates no native goal.

Interpret the current exchange in its context. Discussion can produce evidence, alternatives, and open questions while material choices remain unsettled. Surface those choices and continue routine work within existing delegation. Distinguish agreement on a direction, a request for a saved intent, and authorization to execute it. When a ready intent is requested, materialize and validate its canonical central files and selected retrieval before reporting readiness. Report artifact readiness and native activation separately from their observed evidence.

Status reports identify native goal definition/state, thread or turn activity, Moment incident state, and selected continuation separately, with their observation times. Inspect actual activity and owned job handles before deciding that work has stopped or initiating recovery. Goal-state changes require their own applicable authorization and readback. Where available, retain the observed turn trigger and root-turn identity when explaining activity; later or recovered turns need not be the original goal-triggered turn.

A meaningful handoff can occur inside a still-active native turn. Evaluate it through the selected message, recipient observation and resulting evidence rather than waiting for the entire turn or goal to finish. Transcript investigations retain their covered range and recognized item forms, including `function_call` and `custom_tool_call`; a truncated view, metadata mention or incomplete operation filter cannot establish the absence of a call.

Use direct native agent communication for short questions, steering, progress notices and coordination that needs no durable record. Use Moment when information must survive the sender, be retrieved selectively, support a decision or instruction, or be reused by another session. A short consequential decision may merit persistence; a long disposable transcript may not. A direct message can name a Moment context/incident and the relevant references instead of repeating its payload. Retain a direct exchange only when its outcome becomes consequential, rather than mirroring both channels.

The baseline already has the primitives needed for a handoff. The following are usage patterns, not new kernel types, required workflow phases or an automatically installed personal schema:

| Handoff concern | Existing representation | Guideline |
| --- | --- | --- |
| Purpose and completion | Incident in its context, with optional project association | Preserve the actual objective; a repository or chat is not automatically a separate incident. |
| Source basis | Selected records, references and evidence digests | Name the relevant repository revision, content identity or observed result. A Moment revision orders store changes; it does not identify code or prove a check. |
| Findings and decisions | Immutable atoms with attributable assertions | Distinguish observations, interpretations and unresolved claims. Select supporting evidence; imported summaries acquire no authority automatically. |
| Connections | Typed relations and source references | Express support, contradiction and derivation explicitly when useful. Do not infer containment, agreement or permission from mere connectivity. |
| Continuation | Incident continuation references to selected records | Retain the consequential state, unresolved questions and next useful action, including pending effects or constraints when relevant. Preserve uncertainty instead of inventing a complete account. |

Keep mutable continuation under one explicitly coordinated writer when several agents contribute to the same incident. Other participants can contribute separate observations and evidence; this is not a permanent coordinator role or a kernel-enforced ownership lease. Replacing immutable content uses a new record and an admitted continuation update. On a revision conflict, reread the changed basis before revising the candidate. A session identifier can correlate a contribution but cannot create an independent principal or grant.

Select continuation references as the current basis for recovery. When a new checkpoint supersedes a pending one, replace that current pointer and retain the earlier record through its history or evidence references. An original specification can remain necessary after completion; an obsolete note saying that the same work is pending needs its historical role made explicit. Reconcile meaning and source identity rather than appending every prior pointer or deduplicating by a locator string alone. Immutable records and historical revisions remain intact; the generic kernel does not infer supersession from prose.

Infer personal handoff schemas and reusable prompt templates from an actual retrieval failure or repeated useful payload. Publish a versioned schema only when a consumer needs that validated shape, and admit instructions under current authority. Keep project-native specifications, ledgers and code in their existing owners; reference them at a known basis rather than copying them into competing canonical records. Sharing the store does not require one context for all projects or a common project workflow.

An initial handoff is useful when a recipient can retrieve the purpose, locate the relevant sources, distinguish verified results from open questions, and select its next action without reconstructing the whole conversation. This is an acceptance observation for the participating work, not a claim of automatic organization, compaction interception, model dispatch or improved workload quality. A recipient reads the selected instruction under its current host instructions and permissions; persistent text cannot grant itself authority.

### Historical intake and initial state

Use existing graph records/assertions to retain selected original intent/capture bytes, native identities, source revisions and attributed historical dates. Those observations enter Moment now; source timestamps do not become service receipt times. Backfill need not create an incident when source evidence alone is the useful result. Do not bulk-import history or start project work merely to retain it.

When a central incident is useful, call `incident.create` (MCP `moment_incident_create`) with the actual `incident.status`: `open`, `resting`, `completed` or `cancelled`. Supply `evidence` for a non-open state, using the same `{ sources, method, artifactDigests }` shape as updates. Completed admission requires at least one accessible admitted source; a historical claim of completion alone does not establish current verification. All provided source references must resolve. The response's `StoredIncident.evidence` retains that basis, and `workspace.read`, direct reads and lists share it. Open creation without evidence remains supported.

The caller needs current create authority and, for non-open admission, update authority for the new incident identity. Existing shared credentials and collaborative context/grant scopes still apply; native agent labels do not grant or restrict access. Use ordinary observed-revision and exact-retry keys. Admission creates one current commit event, without a fake open/update sequence or past execution replay. Existing authorized rules may react to that new admission event; importing a source or creating an incident never directly invokes Codex `/goal` or a model. Native work activation remains a deliberate handoff.

## Session conversational memory

Session memory preserves a small working selection of original submitted messages. It complements native goals and Moment continuations, which retain accepted work and implementation progress. Session identity is explicit `{runtimeId, sessionId}` within the local Moment system; a launch directory, project association, or native thread label does not establish access authority. Project adoption is unnecessary. Initial access is owner-local; delegated credentials are refused.

The deterministic `SessionMemory` module retains exact source text/digests, optional exact preceding exchanges, revisioned cache entries, processing cursors, delivery receipts and pending/uncertain work. Default capacity is five entries. A single event-driven `MemoryWorker` calls a configured checker for each eligible input. Its input is the current cache, incoming source selection, and exact referenced exchange material. Its output is unchanged or a replacement list of eligible source IDs with retention weights, optional separate generality estimates and short source notes, and a required outcome explanation of at most 512 Unicode characters. Weights and annotations do not establish instruction authority or promote a proposal into accepted direction. Datum extraction is optional future processing.

Prompt version 6 presents original sources before previous cache assessments and keeps native working-set context explicitly attributed when it contributes to a note. The checker reassesses those fallible notes and numbers from the originals and selects complementary meaning for continuation: standing preferences and distinctive wording, concrete decisions, constraints, corrections and scoped exceptions. A routine invitation to discuss or implement a topic may contribute less than its particular requirements. New decisions compete on meaning; existing membership alone does not protect an entry. The selected list remains a model judgment rather than a deterministic score sort or an optimal-retention guarantee.

Each successful receipt retains the checker's reported `explanation`. `memory.read` exposes the most recent successful `lastAssessment` with its dispatch ID, input sequence, incoming source IDs and basis availability, including originals omitted from the selection. A later failed input cannot masquerade as a new explanation. An unchanged list advances that assessment and processing coverage without changing the cache-content revision. Explanations are unverified model assessments, distinct from source descriptions, exact originals and instruction authority. Older records can lack them; the system does not invent historical reasons.

An entry's note is a derived description. Use exact original wording as its anchor; a self-contained statement may need only its quotation, while a mixed message benefits from a short explanation of referents and qualifications. Quoted wording in a free-form note is not independently validated as an exact span. The separately retained source and digest provide the recoverable original. A structured description/pull-quote projection was evaluated as an isolated presentation experiment; it adds no field or read mode to the current API.

Sources retain authorship evidence independently of their role. Explicit harness notices are skipped; unknown authorship remains unknown. The command adapter currently records hook submissions with unknown authorship. It does not infer personal instructions merely from `role: user` or a lifecycle event. An assistant exchange can explain a user reply while remaining separately attributed context. An unresolved reply stays unresolved when its referenced exchange is unavailable.

`memory.observe` admits one exact delivery without running inference in the caller. `memory.rebuild` admits at most 64 earlier source IDs or selected history captures against the destination's observed cache revision and feeds them through one checker. Original session identities and referenced exchanges remain intact; importing a capture creates no work in its origin session. Reconstruction scans no host history. Input and receipt limits cause explicit refusal instead of silently losing observation coverage. A source text repeated in two distinct submissions remains distinct evidence. Delivery idempotency requires the original delivery ID; native hook fields do not supply a guaranteed unique submission ID.

`memory.read`, `memory.assessments.read`, `memory.focus` and `memory.configure` are the model-facing session operations. A configure request selects the actual session, its observed subscription `expectedRevision`, an `idempotencyKey` and `enabled`. The local owner credential is required; shared credentials retain honest shared attribution. Configuration does not invoke inference. Its revision is independent of cache revision, and an exact older retry cannot resurrect an enrollment disabled later. A read returns subscription/automation state, cache revision, processed/observed input sequences, pending work, gap counts, selected exact sources, the latest successful assessment, worker availability and omitted source IDs. The default response is 16 KiB and the caller can request up to 256 KiB. Metadata and omission references count toward the bound. Under pressure, optional notes, purpose/return-point text and incoming-source lists can be omitted with `omittedFields` JSON pointers into this revision's packet. Selected entry identities/weights remain present. A partial working-set catalog retains `omittedWorkingSetIds`; omitted failure details increase `omittedGapCount`. Request a larger read, or selected assessment detail, before relying on missing meaning. Omission changes the served projection, never the retained value. An envelope that cannot fit its required metadata still refuses explicitly. Larger source recovery uses explicit IDs; every source is associated with the selected session before omission. Successful partial reads do not claim whole-conversation coverage or readiness. Reads neither start a checker nor retry unavailable authentication. The same generated schemas and handlers serve MCP, native calls and CLI.

`moment memory on|off [--runtime ID] [--session ID] [--json]` changes future automatic capture for the selected actual session. The default runtime is `codex`; an actual `CODEX_THREAD_ID` can supply the session. Missing identity refuses. `moment memory configure --file PATH|-` replays an exact reviewed configuration request. A new session is off, project adoption is unnecessary, and earlier messages require an explicit bounded rebuild. `memory.read` reports configured state separately from observed intake/provider coverage; enabled alone does not prove a hook is installed, trusted or loaded. The first automatic intake observed at the current enrollment revision establishes only intake, not successful assessment or comprehension. Turning off retains historical reads and uncertain dispatched work.

`moment memory read|status --runtime ID --session ID [--json]` inspects selected state; an available `CODEX_THREAD_ID` supplies the session default for an explicitly invoked command. `--sources JSON` and `--maximum-bytes N` recover selected originals. Explicit owner-local intake/reconstruction/reconciliation uses `moment memory observe|rebuild|cancel|reconcile --file PATH|-`. These operations remain omitted from every model tool profile and are independent of automatic enrollment. Native labels sharing the owner credential retain its actual shared authority.

`moment memory hooks --runtime ID [--session ID] [--codex-home PATH] [--moment-home PATH]` prints reviewable hook definitions without writing configuration or starting a service. Select a stable host/runtime identity across launches. An explicit `--session ID` limits both generated handlers to that exact native conversation. Other or unidentified sessions return before connecting to Moment, storing input or starting a checker; the filter does not replace the incoming identity or grant authority. Without that option one reusable host definition serves durably opted-in root sessions. Both variants honor enrollment. Unenrolled sessions return before transcript scans, connection or service startup. The projection is a private hint, followed by an authoritative session/revision check before intake and presentation. It is an explicit selector, not an inherited current-thread environment default. The `UserPromptSubmit` handler admits its concrete event and reads the latest completed cache without waiting for inference. `SessionStart` reads that cache on startup, resume, compaction, clear and fork. A new native session has a separate empty cache; a fork does not silently inherit its parent's cache. A session without selected evidence, assessment/processing coverage or meaningful focus remains quiet. The automatic projection is a compact map of current focus, selected descriptions, coverage and recovery handles, including rejected incoming originals when their assessment is available. The native current prompt remains available immediately; pending assessment is explicit even before the first selection. Hook errors are informational and leave the conversation running. An uncertain intake retains the exact private request for replay with its original delivery identity. Subagent events with a supplied child identity are excluded from the initial root-session adapter.

The preceding-exchange adapter reads a bounded tail from the explicit native transcript path under the selected Codex home's `sessions` or `archived_sessions`. It verifies root session identity and recognized message structure, retains the creation-header version as metadata, and selects only visible assistant text. Reasoning and tool payloads are excluded. Exact text parts retain their raw JSONL range digest, file path, part index, available native IDs, per-part provenance type/content kind, and the independently retained client-authored flag. A header's CLI version identifies its source format, not necessarily the daemon that most recently resumed it. Missing, malformed, oversized or out-of-window exchange is unavailable evidence, never an invented explanation.

`moment memory select --file selection.json --codex-home PATH --runtime ID --json` prepares a reviewable rebuild without contacting Moment or invoking a model. The selection contains the destination `session`, its `expectedRevision`, and an ordered `selections` array of `{transcriptPath, sessionId}`. Optional `maximumBytes` bounds the aggregate tail window, defaulting to 1 MiB and capped at 8 MiB across at most eight selected files; `maximumCaptures` defaults to 64. Selection preserves file order followed by source order. Input explicitly marked with harness provenance is excluded; the client-authored flag alone does not establish authorship. Remaining user-role text retains unknown authorship. The output contains `value.input` and coverage for files, omitted captures, oversized parts and missing exchange. With no captured input, `value.input` is null. Review the coverage, save the exact input privately and pass it to `moment memory rebuild --file PATH`. Preserve its delivery ID for reconciliation. This works before project adoption.

### Automatic memory map

Automatic additional context has a default complete UTF-8 budget of 4 KiB, including its preface. The owner-local `maxAutomaticBytes` preference is independent of explicit read ceilings, model context capacity and native hook spill settings. `moment memory hook --maximum-bytes N` can further lower that preference for the invocation. An insufficient minimum receives an informational refusal; the service does not enlarge the requested bound.

The map reserves omission metadata before including whole identities, descriptions and original source bodies. It preserves source attribution and exact bodies/digests when included; it never puts a truncated source under the original digest. `omitted` distinguishes missing references, descriptions, bodies and detailed coverage. Upstream read qualifications remain explicit through `readOmissions` or its omitted-field/count indication. Use `memory.read` for needed originals/current focus and `memory.assessments.read` for retained assessment evidence. A missing active assessment is distinct from an existing assessment omitted for space. Latest-session assessment and active-set retention remain separate.

The hook does not load dormant selections into every prompt, wait for inference or change focus/enrollment. Its local evidence read and its delivered map have separate budgets. Actual model-visible delivery still requires the native integration to be installed, trusted and loaded; serving a bounded string alone does not prove what a model received.

### Reversible working sets

Each actual session begins with one default working set. `memory.focus` reuses a local `purposeKey`, creates a set or explicitly releases an eligible set using `expectedFocusRevision` and an exact `idempotencyKey`. The native agent manages relevance; no classifier result changes focus, authority or native goals. New sets start empty unless `seedFrom` explicitly names a retained set; seeding shares immutable selection values rather than copying source bodies. A set holds a label, optional purpose/return point and a few associated original source IDs. Empty purpose/return-point strings clear those fields. Duration may remain unknown. Selecting a set does not enable automatic memory or queue a checker.

Enrollment revision, focus revision, per-set manifest revision and session cache-content revision are independent. A focus change can leave identical cache content unchanged. Successful unchanged assessments advance the set's manifest revision and processing coverage while preserving the cache-content revision. `memory.read` returns actual `focus`, selected `workingSet`, and distinct latest-session, active-set and selected-set assessments when available. `workingSetId` reads an inactive set without selecting it; `includeWorkingSets` requests a bounded catalog. `moment memory read|status --working-set ID --sets` exposes the same selections.

Input is bound to its set at admission; claim freezes that set's revision, sources, focus observation and profile. A result for dormant A can update A without changing active B. A changed A basis instead retains the result as an explicit revision conflict. Exact older focus retries return their original receipt without restoring an old selection. Pending/unknown work prevents release of its set; releasing the active set also requires a retained replacement. Original sources remain under their independent retention policy.

Fresh operator intake after focus changes needs an explicit `workingSetId`; exact older intake retries keep their admitted target. Automatic hook intake binds the then-active set under its separately checked enrollment. Explicit reconstruction uses `workingSetId` and `expectedWorkingSetRevision`; the legacy default path uses `expectedRevision` and refuses an ambiguous fresh request after focus changes. The conventions cannot be mixed. `moment memory select` can prepare either destination convention without contacting Moment.

`moment memory focus --file PATH|- --json` accepts the exact structured mutation. Its CLI retains an uncertain request privately for exact replay. A readable ID or source reference grants no access: focus is owner-local, source evidence must already be associated with this actual session, and separately attributed exchange sources do not become selectable originals. Initial limits are eight retained sets per session and an 8 MiB component budget for selection values, manifests and focus receipts. No model call or implicit eviction follows from reaching those bounds.

### Work and guidance bindings

A `memory.focus` selection can include `work`, using only the existing `AttachmentTarget` routing fields, and up to eight `guidance` selections. `work: null` clears the target; `guidance: []` clears guidance. Other focus updates preserve existing bindings. This requires neither project adoption nor a new goal: an opaque local purpose remains sufficient when there is no Moment work target. An optional project ID must agree with both the central registry and context manifest. Binding never creates that association or grants permission.

Each guidance binding retains `source`, `capture`, `contentDigest`, `representation`, optional UTF-8 `bodyRange`, `applicability` and `materialOmissions`. The digest identifies the exact chosen whole, selected or ranged bytes, rather than an unmarked truncation. Applicability is bounded to 2 KiB; at most eight material-omission descriptions each use 512 bytes. Different scoped uses of the same capture remain independent annotations; an identical complete binding is redundant. Only locators and annotations enter the working-set manifest. Original guidance bytes remain in their source component, and no binding is added to the cheap checker's conversational input.

Admission verifies current domain access and byte identity. `memory.read.bindings` independently rechecks the same selected owner credential and current policies. Work includes observed context/incident state. Each accessible guidance item carries its original binding `index`, qualified binding and `freshness`; omitted items identify only their kind, original index and unavailable/integrity/component reason. An index refers to the stored binding order, not the filtered result position. A denied external reference is absent from the served binding even when it was admitted earlier. Local conversation evidence and already retained native context have separate owners; this is not retroactive unlearning.

A newer capture or withdrawn source can leave an accessible old selection as `historical`. The service never silently rebinds it. `current-observation` means agreement with the latest recorded source observation, not a new filesystem scan. Explicit refresh and source review remain necessary when freshness matters. Binding reads and focus create no inference, enrollment or native goal activity. A successful binding proves neither that the native agent inspected its body nor that an instruction was adopted.

When a goal change or consequential handoff uses registered guidance, attach/read the relevant work and discover candidates at its actual location. Retrieve the needed body with `guidance.read`, or reuse a relevant verified excerpt actually present. Judge its conditions against the task; retain exact source/capture/digest, selection, applicability and material omissions. The working set can preserve the same binding for return. Record consequential actual use in the goal/handoff; a mutable relevance binding is not a historical use ledger. Ordinary discussion does not need a ceremonial binding or another working set. The [typed example](../../contracts/memory.examples.ts) shows the shared API.

### Assessment history

`memory.assessments.read` selects the actual session and pages newest-first assessment summaries, or selects one `assessmentId` for its retained basis, profile and outcome. Incoming source IDs remain available after eligible full detail is retired. A cursor belongs to its original session, limit and response budget and excludes later assessments. Wrong-session IDs and unknown IDs have the same unavailable response. Reading never queues a checker, retries authentication, changes enrollment or selects focus.

Before possible dispatch, immutable evidence retains ordered source references, prior entries and their notes, exact incoming originals, profile data and request/prompt/schema digests. Exact request and rendered input reconstruction verify those identities against the originals. The native preparation additionally records role instructions, effective model/permission settings, native schema and observed API/version identity. Profiles are data; recovery does not evaluate stored code. The core and raw native result commit before the provider can retire its journal payload. Invalid or oversized results retain explicit qualification; missing legacy basis is not reconstructed from current notes.

The default response is 16 KiB, with an explicit maximum of 256 KiB. Whole components that do not fit appear in `omittedParts`. To recover larger text or canonical JSON, select `part` and a UTF-8 `bodyRange` of at most 128 KiB; the result distinguishes whole and selected digests, offset and total bytes. A range cannot masquerade as the whole component. Preserve UTF-8 boundaries. Metadata itself can exceed a caller's small budget and receives a limit refusal.

`moment memory assessments --runtime ID --session ID --json` lists summaries. `moment memory assessments --file PATH|- --json` accepts the exact typed detail, range or continuation selection. File input owns the complete selection; combining it with separate session/budget flags refuses. Native calls, CLI, generated agent metadata and MCP share this operation and its owner-local access checks.

### Native checker and activation

The worker is disabled without a selected provider. `runtime/session-memory.json` selects checker availability for the host; it does not enroll sessions. Ordinary agents use `memory.configure` for their actual session, after the one-time shared hook installation/trust/load. An owner may enable the qualified Codex worker through this private configuration in the selected Moment home:

```json
{
  "formatVersion": 1,
  "enabled": true,
  "provider": {
    "kind": "codex",
    "credentialFile": "/absolute/private/auth.json",
    "model": "gpt-6-luna"
  }
}
```

The native profile uses the consumed app-server contract in `runtime/codex-api.mjs`, records the actual CLI version, defaults to Luna with low reasoning, and refuses model fallback. Matching API behavior is accepted across release labels; required response, notification, model or permission disagreement produces a scoped diagnostic. Optional provider settings are an absolute `binary`, `timeoutMillis` from 1,000 to 120,000, `maximumJournals` and `maximumJournalBytes`. It starts one owned stdio app-server with private HOME/CODEX_HOME/XDG/workspace directories, external ephemeral access-token authentication and no shared writable auth or refresh state. The selected source must be private, owned and unexpired. Authentication refresh stays with that source's owner. No separately billed API is substituted. Invalid configuration or unavailable optional storage preserves ordinary Moment service operations and reports memory unavailability.

Native profile 5 supplies explicit selectable-source IDs, separately identified context-only exchange IDs and a maximum entry count bounded by the distinct selectable candidates. Prompt 6 treats each original message as one cache unit and keeps annotations scoped to their source and named intent/task. The native array schema carries that count bound; the deterministic executor still rejects duplicate IDs, context-only selections and invalid output instead of repairing their meaning. A retained result from an earlier native profile is refused for recovery under this profile; qualify it with its original implementation or reconcile explicit evidence before upgrading an uncertain dispatch. The checker has no memory hooks, inherited MCP configuration, dynamic tools, shell tool, enabled apps/plugins, or child agents. Its named filesystem profile is read-only and its tool-network permission is disabled; the model service connection still operates. Native OS enforcement follows Codex's resolved platform permissions; a prompt is not a filesystem security boundary. Its fixed selection instructions and structured result schema are retained by digest alongside the actual native model, input basis, usage and latency. These estimates neither establish semantic truth nor authorize implementation.

Provider setup precedes dispatch. Once a result is durably observed and committed, the owned native process exits and its settled instance is removed. An uncertain call retains its dispatch and recovery state rather than being replayed. Automatic recovery applies a matching durable result without another model invocation. The native journal retains observed terminal status and valid output before depending on a turn-start acknowledgment. After possible dispatch, the worker checks that retained evidence once; a confirmed interruption releases the input as cancelled and a completed result can commit even when acknowledgment was lost. Without such proof, the dispatch stays unknown; reads do not retry it. Owner reconciliation must establish observed output, failure, cancellation, or proof that inference never started. Reconciliation wakes work queued during a prior provider's settlement. Provider-preparation failure does not turn an earlier queued wake into an automatic retry. [Storage](storage.md#session-memory-storage) owns bounds and custody.

Activation requires the matching service/catalog and newly connected MCP bridge, explicit provider configuration, and Codex's normal review/trust of the generated hook definitions. Hooks and provider settings are loaded at their respective process/session starts; writing files does not update already loaded clients. Prepare and review changes before coordinating restarts. Existing goals remain independent. The [verification record](../development/verification.md#session-memory-candidate) distinguishes executed native trust/resume/compaction and model checks from ordinary scripted tests. Live native runners record actual versions and qualify the APIs they exercise; the [dependency policy](../development/dependencies.md) owns admission and failure behavior. [Codex hook inputs and trust](https://learn.chatgpt.com/docs/hooks)

## Messages and awareness

The default communication preference above does not remove the durable mailbox. Use it when delivery must survive disconnected participants or requires retained acknowledgment and references. A mailbox notice does not wake a native coding agent by itself, and the current shared owner credential does not provide separate mailboxes for native child labels.

Messages carry a bounded summary and detail references so participants can discover relevant work without loading all histories. Initial limits are 8 KiB of UTF-8 summary text and 32 detail references. Sender identity is recorded by the service. The recipient must have a current admitted incident-read and mailbox-read grant, or be the operator under current policy. Reading a message still rechecks incident policy and access to every referenced detail. A message with inaccessible detail is withheld as a whole rather than returning altered content under its original digest. A response names the request in `inReplyTo` and has its own ID and provenance.

A context retains at most 4,096 messages. Reads are scoped to the authenticated recipient, ordered by stored revision then ID, and paginated with authority-bound opaque cursors. Historical reads recheck current access; acknowledgment filtering follows the selected snapshot. Replies must name a request received from their actual recipient in the same incident.

Delivery is at least once. Exact send retries use the mutation key; recipients deduplicate message IDs. Acknowledgment records delivery processing, not agreement, successful work, or permission to act. Expired messages remain auditable but no longer request new work. Detail retrieval uses ordinary authorized query or artifact operations. Mailbox reads cannot enumerate another principal's messages without a separately admitted administrative operation, which is outside `0.1`.

## Exchange between systems

An `ExchangeBundle` contains selected immutable records and assertion states from one source context and revision. Export checks permission for every included element and reference disclosure. Limit bundles to the transport frame size; split larger transfers into independent bundles with distinct IDs. The digest uses canonical JSON excluding the digest field itself. A digest detects content changes but does not authenticate a peer.

Import authenticates the peer through installed configuration, verifies the bundle digest, and checks its declared source system. Retain foreign references unchanged and record a local import receipt binding peer, bundle, and admission revision. Local policy decides whether imported assertions contribute evidence. They cannot create local grants, replace policy, activate rules, launch executions, or declare themselves trusted. Unknown referenced records remain unresolved and cannot satisfy a condition requiring resolved evidence.

The same `(sourceSystemId, bundle.id)` with identical content is deduplicated; different content is an identity conflict. Local edits never rewrite foreign assertions. A later withdrawal is a new imported state supported by the authenticated source and ordered by its source revision; an older bundle cannot restore newer withdrawn support. Equal-revision contradictory states are rejected. Cross-system atomic commits and automatic transitive trust are outside this contract.


Historical selection accepts the recognized session-header/message structure independently of the release label. Recorded cases include `0.167.0`, `0.167.2` and `0.169.0`; these are evidence examples rather than an allowlist. Retain the observed header version, or `unknown` when absent/unusable, and exact selected byte identity. A creation header does not establish the writer version of every appended frame. An incompatible consumed message shape returns `UNSUPPORTED_MESSAGE_SHAPE`; source custody, session identity, bounded windows and exclusions remain enforced. Selecting history does not start a model or claim complete ingestion.
